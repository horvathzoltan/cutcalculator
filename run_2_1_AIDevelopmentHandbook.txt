1. Bevezetés – A rendszer filozófiája

A CutCalculator fejlesztése során a Copilot:

-   architekturális partner,
-   refaktor‑motor,
-   minőségbiztosítási eszköz,
-   dokumentációs segéd,
-   teszttervező,
-   kódelemző.

A cél:
egy determinisztikus, auditálható, moduláris, drift‑biztos
AI‑fejlesztési pipeline.

A módszertan alapelve:

  A kreatív tervezés és a determinisztikus implementáció szigorú
  szétválasztása.

Ez ipari szinten a legfontosabb minőségbiztosítási elv.

2. Alapelvek (Core Principles)

2.1 Determinisztikus működés

A Copilot csak akkor generálhat kódot, ha:

-   a fájllista jóváhagyva,
-   a kontextus teljes,
-   explicit utasítás érkezett.

Ez a Controlled Code Synthesis minta.

2.2 Kontextusvédelem

A chunk‑kezelés és a handshake megakadályozza:

-   a hiányos inputot,
-   a driftet,
-   a hibás generálást.

Ez a Deterministic Context Loading minta.

2.3 Moduláris workflow

A fejlesztés 10 lépésre bontva, mindegyik külön prompt‑típussal.

Ez a Separation of Concerns minta.

2.4 Emberi jóváhagyás minden kritikus ponton

A Copilot nem dönthet:

-   modulokról,
-   API‑król,
-   architektúráról,
-   viselkedésváltozásról.

Ez a Human‑Approved Change minta.

2.5 Snippet‑alapú módosítás

A Copilot csak diff‑szerű snippeteket adhat meglévő fájlokhoz.

Ez a Minimal Change Set minta.

🔵 4/A. – A két tervezési dokumentum helye a pipeline‑ban

A pipeline elején két dokumentum dolgozik együtt:

    Feature Spec (Egyes)
            ↓
    Architecture Spec (Kettes)
            ↓
    Codegen: Filelist
            ↓
    Chunk-Handshake
            ↓
    Implementáció

Miért így?

-   A Feature Spec → a konkrét feladat
-   Az Architecture Spec → az állandó kontextus
-   A kettő együtt → teljes, stabil input a Copilot számára

Ez ipari szinten a Dual‑Layer Planning Pattern.

------------------------------------------------------------------------

🔵 4/B. – Miért kell két külön tervezési dokumentum?

1) Különböző időskálán változnak

-   Feature Spec → minden új funkciónál
-   Architecture Spec → ritkán, csak nagy változásnál

2) Különböző célközönség

-   Feature Spec → fejlesztő
-   Architecture Spec → architect + Copilot

3) Különböző granularitás

-   Feature Spec → konkrét
-   Architecture Spec → absztrakt

4) Különböző stabilitási követelmények

-   Feature Spec → gyors
-   Architecture Spec → stabil

6. Chunk‑kezelés – Ipari szintű protokoll

6.1 Miért szükséges?

A transformer modellek:

-   nem tudják, hogy hiányzik‑e input
-   nem tudják, hogy egy fájl több chunkból áll
-   nem tudják, hogy a chunkok sorrendje helyes‑e

Ez driftet és hibás generálást okozna.

6.2 A protokoll

1.  A script chunkokra bontja a fájlokat
2.  Minden chunk végén jelölés:
    --- EndOfChunk: <filename> ---
3.  A Copilot minden chunk után megkérdezi:
    „X chunk érkezett. Ez volt az összes?”
4.  A user válaszol:
    -   „Igen, ez volt az összes.” → kontextus teljes
    -   „Nem, jön még.” → várakozás
5.  A Copilot csak teljes kontextus után dolgozhat

6.3 Sorrend

A chunkok sorrendje lexikálisan rendezhető:

    *_part_aa.txt
    *_part_ab.txt
    *_part_ac.txt

Ez determinisztikus.

🎯 1) A prompt mint szerződés

A gyenge prompt: „írj egy dialogot”.

A jó prompt:

-   definiálja a kontextust
-   definiálja a stílust
-   definiálja a minőséget
-   definiálja a tiltásokat
-   definiálja a workflow‑t
-   definiálja a kódgenerálás lépéseit
-   definiálja a projekt nyelvét

A prompt nem kérés, hanem szerződés a fejlesztő és az AI között.

Ez a szerződés garantálja:

-   a determinisztikus működést
-   a driftmentességet
-   a minőséget
-   a konzisztenciát

------------------------------------------------------------------------

🎯 2) A prompt mint DSL (Domain‑Specific Language)

A CutCalculator promptjai már nem „szövegek”.

Ez egy CutCalculator Prompt DSL:

-   saját szókészlettel
-   saját szabályokkal
-   saját ritmussal
-   saját architektúrával
-   saját vizuális identitással

Ezért tudunk:

-   konzisztens
-   audit‑barát
-   stílusos
-   gyors
-   hibamentes

kódot generálni.

A prompt a projekt nyelve.
