- a Presenter **ne tartalmazzon UI‑logikát**

# ⭐ **ORDER ITEM ÁLLAPOTGÉP INTEGRÁCIÓ – PONTONKÉNTI TERV**

A terv **három rétegre** bontja a feladatot:

1) **Model / Domain** – OrderItem állapotai
2) **UI State Machine** – Workbench kiterjesztése Item‑re
3) **Presenter** – domain műveletek, UI‑logika nélkül

És mindhárom rétegben **szigorúan külön tartjuk** a Header és Item logikát.

---

# ⭐ 1) DOMAIN SZINT – OrderItem állapotok (külön a Header‑től)

A Header állapotai:

- EmptySystem
- NewHeaderEditing
- ListNoSelection
- HeaderSelected
- HeaderEditing

Az Item állapotai **külön enum‑ba kerülnek**, nem keverednek:

```cpp
enum class ItemState {
    NoHeaderSelected,   // nincs hova tenni tételt
    NoItems,            // van header, de nincs tétel
    ItemSelected,       // van kiválasztott tétel
    ItemEditing,        // tétel mező módosítva
    NewItemEditing      // új tétel létrehozása
};
```

**Miért külön enum?**
Mert:

- a Header és Item állapotok **nem ugyanazt a dimenziót** írják le
- a Header állapot nem mond semmit arról, hogy az Item milyen állapotban van
- így a kód **nem keveredik**, nem lesz spagetti

---

# ⭐ 2) WORKBENCH SZINT – Két külön állapotgép, egy közös UiState

A Workbench jelenleg:

- `resolveState()` → Header állapot
- `applyState()` → UiState mátrix

Most ezt **kibővítjük**, de NEM keverjük össze.

### 2.1. Új metódus:

```cpp
ItemState resolveItemState() const;
```

Ez kizárólag az Item állapotot számolja ki:

- van‑e header
- van‑e item
- van‑e kiválasztott item
- módosult‑e az item mező
- új item létrehozása folyamatban van‑e

### 2.2. UiState kibővítése

A jelenlegi UiState:

```cpp
struct UiState {
    bool listVisible;
    bool listPlaceholderVisible;
    ...
    bool itemAddEnabled;
    bool itemDeleteEnabled;
};
```

Ezt **nem bővítjük tovább**, hanem:

👉 **két külön mátrixot hozunk létre**:

- `HEADER_UI_STATE_MAP`
- `ITEM_UI_STATE_MAP`

Mindkettő saját enum alapján.

### 2.3. applyState() → kétlépcsős lesz

```cpp
void OrderWorkbench::updateUIState()
{
    State hs = resolveState();
    ItemState is = resolveItemState();

    applyHeaderState(hs);
    applyItemState(is);
}
```

Ez garantálja:

- a Header és Item UI‑logika **nem keveredik**
- a kód **átlátható**
- a mátrixok **külön élnek**
- a Workbench **determinista** marad

---

# ⭐ 3) PRESENTER SZINT – Domain műveletek, UI‑logika nélkül

A Presenter:

- `newOrder()`
- `loadOrder()`
- `saveOrder()`
- `deleteOrder()`
- `addItem()`
- `deleteItem()`

Mostantól:

### 3.1. A Presenter NEM dönt UI‑ról
Csak:

```cpp
if (auto* wb = qobject_cast<OrderWorkbench*>(parent()))
    wb->updateUIState();
```

### 3.2. Item mezőváltozás figyelése
Ugyanúgy, mint a Header esetén:

- minden QTableWidget cella módosítás → `updateUIState()`

### 3.3. ItemEditing felismerése
A Workbench:

- összehasonlítja a registryben lévő eredeti itemet
- a táblázatban lévő aktuális itemmel
- ha eltérés → `ItemEditing`

---

# ⭐ 4) UI ELKÜLÖNÍTÉS – Header és Item UI nem keveredik

### 4.1. Header UI elemek:

- headerPanel
- headerPlaceholder
- headerToolbar

### 4.2. Item UI elemek:

- itemTable
- itemPlaceholder
- itemToolbar

A két rendszer:

- külön mátrix
- külön apply metódus
- külön resolve metódus
- külön placeholder szöveg
- külön toolbar logika

**Soha nem érintik egymást.**

---

# ⭐ 5) KÓDSTRUKTÚRA – A tiszta szétválasztás garantálása

A Workbench fájlban:

```
resolveState()              // Header
resolveItemState()          // Item

applyHeaderState()          // Header UI
applyItemState()            // Item UI

updateHeaderPlaceholderText()
updateItemPlaceholderText()
```

A Presenter fájlban:

```
newOrder()
loadOrder()
saveOrder()
deleteOrder()

addItem()
deleteItem()
```

**Nincs keresztlogika.
Nincs keveredés.
Nincs spagetti.**

# ⭐ 6) VÉGSŐ GARANCIA – A két állapotgép SOHA nem keveredik

A Header és Item állapotok:

- külön enum
- külön resolve
- külön apply
- külön mátrix
- külön UI elemek
- külön placeholder
- külön toolbar

Ez a legmagasabb szintű architektúra, amit egy ERP‑szerű Workbenchben alkalmazni lehet.
