Rendben, akkor A) – vagyis a két külön függvényes megoldás lesz az alap.
Ez a döntés nagyon jó, mert ettől kezdve a Calculation modul két külön
szerződésű, két külön pipeline‑t kezel, és a FormulaEngine csak egy
általános számoló motor marad.

Az alábbiakban összerakom a végleges, tiszta, p1…pN pontokba rendezett
architekturális tervet, amely:

-   csak a jelenlegi, valós FormulaEngine‑re épül,
-   nem tartalmaz semmilyen régi DSL‑t,
-   figyelembe veszi a RawCut / RawKit szétválasztást,
-   engine‑alapú validációt használ,
-   szerződésalapú output‑ellenőrzést ad,
-   és egységes hibakezelést vezet be.

📐 Új Calculation + FormulaEngine architektúra – p1…pN terv

p1 — A FormulaEngine DSL végleges, valós szintaxisának rögzítése

A DSL kizárólag azt tudja, amit a kód implementál:

-   literálok (szám, string)
-   változók
-   assignment
-   aritmetikai operátorok
-   relációs operátorok
-   ternary ? :
-   opt node (opt: flag ? expr)
-   több soros script (Sequence)
-   return node (Assignment‑list visszaadás)
-   skip‑kezelés (opt miatt)
-   függvényhívások (FunctionRegistry)

Nincs többé: - len:, qty:, choose: prefix DSL
- domain‑függvények (qty_fixed, qty_perArea, stb.)
- implicit qty‑szorzás
- implicit material‑választás

A DSL dokumentációját frissíteni kell (külön fájlban).

------------------------------------------------------------------------

p2 — A NeedCalculator két külön eval‑függvényre válik szét

Ez a te választásod: A)

-   evalFormulaCut(const OrderLine&, const NeedCalculationDetail&) -> RawCut
-   evalFormulaKit(const OrderLine&, const NeedCalculationDetail&) -> RawKit

Mindkettő:

-   feltölti a FormulaEngine input változóit,
-   futtatja a FormulaEngine‑et,
-   kiolvassa a szerződés szerinti output változókat,
-   hibát dob, ha bármely kötelező output hiányzik.

Ez domain‑tiszta, bővíthető, és egyértelmű.

------------------------------------------------------------------------

p3 — Két külön output modell: RawCut és RawKit

A jelenlegi RawCut marad, és mellé jön:

    struct RawKit {
        QUuid materialId;
        int qty;
    };

A RawCut:

    struct RawCut {
        QUuid materialId;
        int requiredLength;
        int qty;
    };

A pipeline:

-   Cutting: RawCut → Piece → Aggregation
-   Kitting: RawKit → KitItem

------------------------------------------------------------------------

p4 — FormulaContract bevezetése (Cut vs Kit szerződés)

A validáció és a runtime is ezt használja.

Cutting contract:

-   allowedInputs = { w, h, qty, handler, owner, color, externalId,
    product }
-   requiredOutputs = { requiredLength, qty }
-   optionalOutputs = { material }

Kitting contract:

-   allowedInputs = ugyanaz
-   requiredOutputs = { qty }
-   optionalOutputs = { material }

Ez a szerződés lesz a rendszer „igazsága”.

------------------------------------------------------------------------

p5 — Engine‑alapú validáció bevezetése

A NeedCalculationDetailRegistry jelenlegi validációja elavult (len:,
qty:, stb.).

Új validáció:

    bool isFormulaValid(const QString& f, DetailKind kind) {
        FormulaContract c = (kind == Cutting)
            ? cuttingContract()
            : kittingContract();

        return FormulaEngine::analyze(f, c).ok;
    }

A FormulaEngine::analyze():

1.  dummy input változók feltöltése
2.  FormulaEngine::eval() futtatása
3.  hibák ellenőrzése
4.  readVars ⊆ allowedInputs
5.  requiredOutputs ⊆ writtenVars

Ez 100% konzisztens lesz a runtime‑mal.

------------------------------------------------------------------------

p6 — A régi DSL teljes eltávolítása

A következő prefixek és minták teljesen megszűnnek:

-   len:w-20
-   qty:fixed:3
-   qty:perArea:...
-   choose:
-   opt: régi formája (opt:flag:+expr)

A parserben marad az opt: token, mert az AST‑ben működik, de a régi
dokumentációt törölni kell.

A NeedCalculationDetailRegistry‑ből minden régi DSL‑validáció törlendő.

------------------------------------------------------------------------

p7 — Egységes hibakezelés

Három szint:

1) FormulaEngine szint

Minden hiba automatikusan logolódik:

    catch (const QString& err) {
        zEventERR("FormulaEngine error: " + err);
        return EvalResult::failure(code, err);
    }

2) evalFormulaCut / evalFormulaKit szint

Detail ID‑vel együtt logol:

    if (!r.ok) {
        zEventERR(QString("Formula error in detail %1: %2")
                  .arg(detail.id.toString(), r.error));
        throw r.error;
    }

3) Pipeline szint

A hibás detailt WARN‑nal jelzi, és továbblép:

    catch (const QString& err) {
        zEventWARN("Cutting formula error: " + err);
        continue;
    }

Ez átlátható, diagnosztizálható rendszert ad.

------------------------------------------------------------------------

p8 — VariableRepository globális állapotának kiváltása (terv szinten)

A jelenlegi engine globális változótárat használ.

Ez működik, de:

-   validáció és runtime ugyanazt a globális állapotot piszkálja,
-   párhuzamos futásnál törik,
-   debug snapshot is globális.

Terv:

-   VariableRepository → példányosítható VariableContext
-   FormulaEngine::eval() → kap egy contextet
-   eval() visszaadja a contextet is

Ez később bevezethető, nem sürgős.

------------------------------------------------------------------------

p9 — A NeedCalculator pipeline tisztítása

Cutting:

    RawCut raw = evalFormulaCut(line, detail);
    auto pieces = explodePieces(line, raw);
    return CutAggregator::aggregate(pieces);

Kitting:

    RawKit raw = evalFormulaKit(line, detail);
    return assembleKitItem(line, raw);

Nincs több implicit logika, nincs több rejtett DSL.
