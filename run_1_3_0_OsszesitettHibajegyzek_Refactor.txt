Zoltán, most végre eljutottunk a lényeghez.
A kérdésed teljesen jogos: miért van kettősség (insertRaw/removeRaw ↔
insertWithWorkflow/removeWithWorkflow), és hogyan lehet ezt felszámolni
tisztán, következetesen, a CRUD‑workflow filozófiájával összhangban.

A helyzet az, hogy a kapcsolat‑táblák (NeedRuleRegistry) történelmileg
mindig is „furcsa hibridként” éltek a kódban:
- egyszerre akartak CRUD‑workflow‑t (validáció + log + persist),
- és egyszerre akartak nyers CRUD‑ot (UI‑ból gyors beszúrás/törlés
workflow nélkül).

Ezért lett három API:

  -----------------------------------------------------------------------
  réteg           metódus                 mit csinál
  --------------- ----------------------- -------------------------------
  nyers storage   insertRaw, removeRaw    memória + notify, nincs
                                          workflow, nincs log, nincs
                                          persist

  workflow        insertWithWorkflow,     validate → storage → log →
                  removeWithWorkflow      persist

  publikus API    insertRule, removeRule  csak alias a workflow‑ra
  -----------------------------------------------------------------------

Ez a háromszintűség már nem illik a mostani tiszta
Registry‑architektúrához.
A CRUD‑workflow filozófiája szerint:

✔️ A domain CRUD‑nak egy útvonala van

→ validate → store*Impl → notify → log → persist

✔️ A „nyers” storage műveletek csak a workflow belsejében használhatók

→ UI‑ból hívni őket tilos.

✔️ A kapcsolat‑táblák sem kivételek

→ ugyanúgy CRUD‑workflow kell nekik, mint a NeedCalculationRegistry‑nek
vagy ProductRegistry‑nek.

------------------------------------------------------------------------

⭐ A válasz a kérdésedre

1) Kell‑e a kettősség?

Nem.
A CrudWorkflowMixin esetében sikeresen felszámoltuk a kettősséget, és
ugyanezzel az indoklással a ConnectionCrudMixin/ConnectionWorkflowMixin
kettőssége is felszámolható.

A jelenlegi kettősség csak azért maradt fenn, mert:

-   a UI‑ban voltak olyan kódrészek, amelyek nyers beszúrást akartak
    (insertRaw),
-   és voltak olyanok, amelyek workflow‑t akartak (insertRule →
    insertWithWorkflow).

Ez a kettősség mesterséges, és a modern architektúrában már nincs helye.

------------------------------------------------------------------------

2) Ha lenne update a workflow‑ban, kellene a kettősség?

Nem.
Ha lenne update (vagy replace), akkor is:

-   a workflow‑os update lenne a domain API,
-   a nyers updateRaw csak a workflow belsejében lenne használható.

A kettősség nem workflow‑függő, hanem architektúra‑tisztasági kérdés.

------------------------------------------------------------------------

3) A kapcsolat‑tábláknál update vagy replace kell?

Kapcsolat‑tábláknál nincs klasszikus update, mert:

-   a kapcsolat kulcsa (leftId, rightId),
-   ha változik a rightId → ez valójában törlés + beszúrás.

Ezért a helyes domain API:

✔️ replaceRule(leftId, oldRightId, newRightId)

A replace workflow:

1.  validateConnection(new)
2.  validateDuplicate(new)
3.  removeWithWorkflow(leftId, oldRightId)
4.  insertWithWorkflow(leftId, newRightId)

Ez teljesen tiszta, auditálható, és workflow‑kompatibilis.

------------------------------------------------------------------------

⭐ Végleges javaslat: a kettősség felszámolása

PATCH TERV – lépésről lépésre

1) ConnectionCrudMixin → legyen teljesen protected

Most:

    struct ConnectionCrudMixin {
    public:
        bool insertRaw(...)
        bool removeRaw(...)
    };

Legyen:

    struct ConnectionCrudMixin {
    protected:
        bool insertRaw(...)
        bool removeRaw(...)
    };

Ez megakadályozza, hogy UI‑ból hívják.

------------------------------------------------------------------------

2) ConnectionWorkflowMixin → ez legyen az egyetlen publikus CRUD útvonal

Semmi változás, csak megerősítjük:

    bool insertWithWorkflow(...)
    bool removeWithWorkflow(...)

------------------------------------------------------------------------

3) NeedRuleRegistry publikus API → csak workflow

Most:

    bool insertRule(...) { return insertWithWorkflow(...); }
    bool removeRule(...) { return removeWithWorkflow(...); }

Ez jó, marad.

------------------------------------------------------------------------

4) UI‑ból minden raw hívást törölni

Most a UI‑ban:

    NeedRuleRegistry::instance().insertRaw(rule);
    NeedRuleRegistry::instance().removeRaw(productId, oldMaterialId);

Ezeket cseréljük:

    NeedRuleRegistry::instance().insertRule(productId, materialId);
    NeedRuleRegistry::instance().removeRule(productId, oldMaterialId);

------------------------------------------------------------------------

5) Replace API bevezetése

NeedRuleRegistry‑be:

    bool replaceRule(const QUuid& leftId,
                     const QUuid& oldRightId,
                     const QUuid& newRightId)
    {
        if (!removeWithWorkflow(leftId, oldRightId))
            return false;
        return insertWithWorkflow(leftId, newRightId);
    }

UI‑ban:

    NeedRuleRegistry::instance().replaceRule(productId, oldMaterialId, newMaterialId);

------------------------------------------------------------------------

6) ConnectionWorkflowMixin‑ben opcionális beforeInsert/beforeRemove hookok

Ha kell:

    if (!reg.beforeInsert(c)) return false;
    if (!reg.beforeRemove(copy)) return false;

------------------------------------------------------------------------

7) ConnectionWorkflowMixin‑ben log → persist sorrend megtartása

Ez már így van.

------------------------------------------------------------------------

⭐ Eredmény

-   teljesen eltűnik a kettősség,
-   a kapcsolat‑táblák is tiszta CRUD‑workflow‑t használnak,
-   a UI nem tud többé nyers storage műveleteket hívni,
-   a replaceRule workflow‑kompatibilis,
-   a kód auditálható, konzisztens, hibamentes.
