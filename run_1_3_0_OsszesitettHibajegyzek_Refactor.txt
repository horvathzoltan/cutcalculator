Zoltán, ez most egy nagyon jó pont, mert a validátorod jelenleg nem
végez karakterkészlet‑ellenőrzést, és emiatt engedi át a hibás kódokat.
A kérdésed teljesen jogos:

  „Elegendő csak ezt átírni? Ha igen, kellene egy lépésenkénti terv.”

Igen: elegendő a validátorban bevezetni egy karakterkészlet‑ellenőrzést,
és ehhez adok egy tiszta, lépésenkénti tervet + végül egy patch‑tervet.

De előtte: rögzítsük a dokumentációs alapelveket, ahogy kérted.

📘 1. Dokumentációs alapelvek a barcode‑okról (rögzíthető a projektben) <- doksi kész, ezzel már nem kell foglalkozni! de nem törlöm ki a pontot.

Ezeket érdemes egy docs/barcode_rules.md vagy BarcodeValidator.h
kommentblokkban rögzíteni.

Barcode alapelvek (ipari szabványok alapján)

-   A barcode egy egységes azonosító, nem tartalmazhat vizuális törést.

-   Whitespace (szóköz, tab, newline) TILOS, mert:

    -   vizuálisan szétszedi a kódot,
    -   több kódnak látszik,
    -   CSV‑ben, logokban, UI‑ban szétesik,
    -   szkenner hibát okozhat.

-   Csak a következő karakterek engedélyezettek:

    -   A–Z
    -   0–9
    -   - (kötőjel)

-   Ékezetes betűk TILOSAK.

-   Speciális karakterek TILOSAK (# / \ @ ! ? % * + stb.).

-   A barcode formátuma:

        PREFIX + TOKEN + "-" + SLUG

-   A barcode determinista, kompakt, szóközmentes azonosító.

Ez a dokumentáció később nagyon sok félreértést megelőz.

------------------------------------------------------------------------

🧩 2. Miért engedi át most a validátor a hibás kódokat?

Mert a checkAndRegister_impl():

-   csak üres stringet ellenőriz,
-   csak collisiont ellenőriz,
-   csak registry‑be írást ellenőriz,
-   DE NEM ellenőrzi a karakterkészletet.

Ezért:

    "ABC 123" → trimmed → "ABC 123" → OK
    "ABC#123" → OK
    "ÁBC123" → OK
    "ABC/123" → OK
    "ABC\123" → OK

A validátor jelenleg mindent átenged, ami nem üres és nem ütközik.

🛠 3. Lépésenkénti terv a javításhoz

LÉPÉS 1 — Dokumentáljuk a megengedett karakterkészletet

(A fentiek alapján.)

LÉPÉS 2 — Bevezetünk egy regexet a validátorba

Ez a regex ipari standard:

    static QRegularExpression allowed("^[A-Z0-9-]+$");

LÉPÉS 3 — Normalize + uppercase a validáció előtt

Ez már megvan a slug‑generátorban, de a validátorban is kell:

-   ékezetek eltávolítása,
-   uppercase,
-   whitespace eltávolítása (trim).

LÉPÉS 4 — Ha a regex nem illeszkedik → hiba

CSV módban ctx->addError(), UI módban outErrorMessage.

LÉPÉS 5 — Csak ezután jöhet a collision check és a registry‑be írás

LÉPÉS 6 — Tesztek frissítése

A mostani teszted jó, csak a validátor hiányos.

🧷 4. Patch‑terv (minimális, tiszta, ipari)

A checkAndRegister_impl() elejére, az üres ellenőrzés UTÁN, a collision
check ELŐTT:

    // 1/b) Karakterkészlet ellenőrzés
    QString normalized = code.normalized(QString::NormalizationForm_D);
    normalized.remove(QRegularExpression("\\p{Mn}")); // ékezetek le
    normalized = normalized.toUpper();

    static QRegularExpression allowed("^[A-Z0-9-]+$");

    if (!allowed.match(normalized).hasMatch()) {
        const QString msg = QString("Invalid characters in barcode: %1").arg(code);

        if (mode == Mode::CSV) {
            ctx->addError(ctx->currentLineNumber(), msg, code, name);
        } else {
            *outErrorMessage = msg;
        }

        zEventERROR(msg);
        return false;
    }

Ezután a további logika változatlan maradhat.
