Zoltán, akkor most összerakom a teljes, végrehajtható, lépésről‑lépésre
követhető tervet a RegistryStore / RegistryDomain / RegistryEngine
szétválasztására.
Ez nem elmélet, hanem konkrét műveleti lista, amit ha sorban
végigviszel, a rendszered egy tiszta, moduláris, auditálható
architektúrává áll össze.

A terv három fázisra bomlik:

1.  Új architektúra létrehozása (új fájlok, új osztályok)
2.  RegistryEngine átalakítása (a három réteg összekötése)
3.  Domain registryk átvezetése (Material, Product, NeedRule, Barcode)

Mindegyik fázis konkrét, végrehajtható lépésekre van bontva.

------------------------------------------------------------------------

🟦 FAZIS 1 — Új architektúra létrehozása

1.1. Hozd létre az új fájlt:

common/registry/base/registry_store.h

Tartalma:

-   RegistryStore<TEntity> osztály
-   kizárólag storage + lookup API
-   semmi virtual, semmi domain, semmi workflow

Konkrét teendő:

-   Vágd ki a RegistryEngineBase‑ből:
    -   _items + ItemStore
    -   insertInternal, updateInternal, removeInternal
    -   readAll, all, findIf, findAll, existsBy, findById, findByPair
    -   add, addAll, setAll
    -   subscribeItemsChanged, onItemsChanged

És tedd át a RegistryStore<TEntity>‑be.

------------------------------------------------------------------------

1.2. Hozd létre az új fájlt:

common/registry/base/registry_domain.h

Tartalma:

-   RegistryDomain<TEntity> mixin
-   kizárólag domain hookok

Konkrét teendő:

-   Vágd ki a RegistryEngine‑ből:
    -   validateDomain
    -   validateDuplicate
    -   validateConnection
    -   validateBarcode
    -   validateCollision
    -   beforeInsert, afterInsert
    -   beforeUpdate, afterUpdate
    -   beforeRemove, afterRemove
    -   onInsertLog, onUpdateLog, onRemoveLog
    -   onRegisterLog, onRetireLog
    -   onLoadLog
    -   persist

Minden hook alapértelmezése legyen no‑op.

------------------------------------------------------------------------

1.3. Hozd létre az új fájlt:

common/registry/base/registry_engine2.h
(ideiglenes név, amíg át nem áll minden)

Tartalma:

-   új
    RegistryEngine<TEntity, WorkflowPolicy, Domain = RegistryDomain<TEntity>>
-   öröklés:
    -   RegistryStore<TEntity>
    -   Domain
    -   WorkflowPolicy

Konkrét teendő:

-   A régi RegistryEngine CRUD delegálását tedd át ide:
    -   insert(e) → WorkflowPolicy::insert(*this, e)
    -   update(e)
    -   remove(id)
    -   remove(leftId, rightId)
    -   load(items)
-   Semmi domain hook nem marad itt
-   Semmi storage API nem marad itt
-   Ez csak a „ragasztó” lesz

------------------------------------------------------------------------

🟩 FAZIS 2 — RegistryEngineBase és RegistryEngine tisztítása

2.1. A régi RegistryEngineBase → töröld vagy jelöld deprecated‑nek

Miután a RegistryStore átveszi a szerepét, a régi engine base:

-   vagy teljesen törölhető,
-   vagy átmenetileg #pragma message("deprecated").

------------------------------------------------------------------------

2.2. A régi RegistryEngine → fokozatosan kiváltjuk

Amíg minden registry át nem áll az új engine‑re, a régi engine:

-   maradjon érintetlen,
-   de ne bővítsd tovább.

------------------------------------------------------------------------

🟧 FAZIS 3 — Domain registryk átvezetése az új architektúrára

Ezt registrynként kell megtenni.

3.1. MaterialRegistry átvezetése

Konkrét lépések:

1.  A headerben cseréld le az öröklést:

Régi:

    class MaterialRegistry
        : public RegistryEngine<MaterialMaster, CrudWorkflowPolicy>

Új:

    class MaterialRegistry
        : public RegistryEngine<MaterialMaster, CrudWorkflowPolicy, MaterialDomain>

2.  Hozz létre egy új fájlt:
    materials/registry/material_domain.h

3.  Ebbe tedd át a Material‑specifikus hookokat:

-   validateDomain
-   validateDuplicate
-   beforeInsert
-   beforeUpdate
-   onInsertLog
-   onUpdateLog
-   onRemoveLog
-   persist

4.  A MaterialRegistry.cpp‑ben töröld a hook implementációkat.

5.  A MaterialRegistry csak lookup API‑t tartalmazzon:

-   findByType
-   findByShape
-   findByColor

------------------------------------------------------------------------

3.2. ProductRegistry átvezetése

Ugyanaz a minta:

1.  Új fájl: products/registry/product_domain.h
2.  Hookok átmozgatása
3.  RegistryEngine öröklés cseréje
4.  ProductRegistry.cpp tisztítása

------------------------------------------------------------------------

3.3. NeedRuleRegistry átvezetése

Itt fontos:

-   validateConnection a Domain‑be kerül
-   validateDuplicate a Domain‑be kerül
-   beforeInsert, afterInsert, onInsertLog, onRemoveLog, persist →
    Domain

Új fájl:
needs/registry/need_rule_domain.h

------------------------------------------------------------------------

3.4. BarcodeRegistry átvezetése

Ez a legösszetettebb, mert:

-   validateBarcode
-   validateCollision

Új fájl:
barcodes/registry/barcode_domain.h

------------------------------------------------------------------------

🟪 FAZIS 4 — Workflow policy-k tisztítása

4.1. A workflow policy-k csak Domain hookokat hívjanak

Ellenőrizd:

-   reg.validateDomain
-   reg.validateDuplicate
-   reg.validateConnection
-   reg.validateBarcode
-   reg.validateCollision
-   reg.beforeInsert
-   reg.afterInsert
-   reg.persist

Minden hívás működni fog, mert a Domain mixin biztosítja.

------------------------------------------------------------------------

🟫 FAZIS 5 — Mixinek ellenőrzése

A mixinek (BarcodeIndexMixin, BarcodeLookupMixin, HierarchyMixin):

-   csak a RegistryStore API-ját használják (findIf, readAll, existsBy)
-   semmi domain hookot nem érintenek

Ezért nem kell őket módosítani.

------------------------------------------------------------------------

🟩 FAZIS 6 — RegistryManager és RegistryCatalog ellenőrzése

A RegistryEngine továbbra is örökli a RegistryBase‑t →
a regisztrációs mechanizmus változatlanul működik.

Nincs teendő.
